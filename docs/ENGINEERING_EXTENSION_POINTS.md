**Status:** STABLE  
**Extension Policy:** All extension points documented here are approved. Any feature not listed requires architectural review.

## New Verification Profile

To add a new verification profile:

**Entry Point:** `runtime/foundation/verification/profiles.py`

**Process:**
1. Add new profile to `_PROFILES` dictionary
2. Create corresponding `VerificationTask` entries
3. Add tasks to `_VERIFY_{PROFILE_NAME}_TASKS` tuple
4. Ensure all tasks are pure functions returning violations/results

**Example:**
```python
_VERIFIED_NEW_TASKS = (
    VerificationTask(
        id="new-feature-check",
        name="New feature check",
        profile="newprofile",
        commands=["python -m tools.new_checker"],
        category=VerificationCategory.CAPABILITY,
        scope=VerificationScope.NEWPROFILE,
        estimated_duration_seconds=60,
    ),
)

_PROFILES["newprofile"] = VerificationProfile(
    name="newprofile",
    scope=VerificationScope.NEWPROFILE,
    description="New verification profile",
    tasks=_VERIFIED_NEW_TASKS,
)
```

**Constraints:**
- Tasks must not duplicate existing checks
- Commands must be deterministic
- Profile names must be lowercase

## New Integrity Rule

To add a new integrity rule:

**Entry Point:** `runtime/foundation/integrity/rules.py`

**Process:**
1. Add rule function
2. Register in `_RULE_CHECKS` dispatch table
3. Define rule ID as `ARCH-XXX`

**Example:**
```python
def check_custom_rule(graph: ArchitecturalGraph) -> list[Violation]:
    """ARCH-029: Custom rule description."""
    violations: list[Violation] = []
    # Rule logic here
    return violations

_RULE_CHECKS["ARCH-029"] = check_custom_rule
```

**Constraints:**
- Rule functions are pure: take graph, return violations
- Never modify files
- Never repair code
- Rule IDs must follow `ARCH-XXX` pattern

## New Knowledge Index Entity

To add a new knowledge entity type:

**Entry Points:**
- `runtime/foundation/knowledge/models.py` – Entity model
- `runtime/foundation/knowledge/indexer.py` – Extraction logic

**Process:**
1. Add new Entry dataclass to models.py
2. Add extraction logic to indexer.py
3. Return entity from `build_index()`

**Example:**
```python
@dataclass(frozen=True)
class NewEntityEntry:
    name: str
    path: str

def _extract_new_entities(cross_layer_map: dict) -> list[NewEntityEntry]:
    entities: list[NewEntityEntry] = []
    # Extraction logic
    return entities
```

**Constraints:**
- New entities must be immutable dataclasses
- Must not modify existing artifacts

## New Diagnostic Command

To add a new diagnostic command:

**Entry Point:** `runtime/verify.py`

**Process:**
1. Add `cmd_newcommand()` function
2. Register in `main()` dispatch table

**Example:**
```python
def cmd_newcommand() -> int:
    from runtime.foundation.intelligence.diagnostics import SomeDiagnostics
    diagnostics = SomeDiagnostics()
    report = diagnostics.analyze()
    print(json.dumps(report.to_dict(), indent=2))
    return 0

# In main():
if command == "newcommand":
    return cmd_newcommand()
```

**Constraints:**
- Commands must be idempotent
- Must not modify repository state
- Exit code 0 for success, 1 for failure

## New Engineering Metric

To add a new engineering metric:

**Entry Points:**
- `runtime/system/observability/analytics.py`
- `runtime/system/observability/metrics.py`

**Process:**
1. Add metric computation to AnalyticsEngine
2. Include in `compute()` output
3. Register in knowledge indexer if persistent

**Constraints:**
- Metrics must be deterministic
- Must not require external services

## New Runtime Artifact

**This is NOT an approved extension point.**

Runtime artifacts are generated by the Verification Runtime orchestrator. Adding new artifacts requires modification of the orchestrator, which is part of the frozen core.

To add new verification data, extend an existing artifact or add a new verification task that produces output to the standard report.

---

## Extending CI Workflows

**This is NOT an approved extension point.**

The CI workflow architecture is frozen at v1.0.0. To add CI functionality:

1. Use existing workflow triggers
2. Extend job steps within existing workflows
3. Do not create new workflow files (except for release/dependency maintenance)

## Extension Review Process

For extensions not covered above:

1. Create RFC in documentation
2. Demonstrate no duplication
3. Show value to Financial OS development
4. Get architectural review approval

Extensions must not modify:
- Backend business logic
- Frontend business logic
- DTOs
- Capabilities
- Mappers
- Runtimes
- Planner
- Observability logic
- Integrity logic
- Knowledge logic
- Engineer workspace

Only documentation, version metadata, CLI help, and repository configuration may be modified.
