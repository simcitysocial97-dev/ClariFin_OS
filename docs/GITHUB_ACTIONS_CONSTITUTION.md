## 1. Workflow Responsibilities

Each GitHub Actions workflow has **exactly one responsibility**. No workflow performs more than one verification domain.

| Workflow | Responsibility |
|----------|---------------|
| `backend-verify.yml` | Run `python runtime/verify.py backend` |
| `frontend-verify.yml` | Run `python runtime/verify.py frontend` |
| `quality.yml` | Run `python runtime/verify.py quick` |
| `verification-runtime.yml` | Run `python runtime/verify.py runtime` |
| `golden.yml` | Run `python runtime/verify.py golden` |
| `mutation.yml` | Run `python runtime/verify.py mutation` |
| `playwright.yml` | Run `python runtime/verify.py playwright` |
| `release.yml` | Build frontend distribution + package release artifacts |
| `dependency-update.yml` | Scheduled dependency health monitoring |

**Rule:** A workflow must not inline engineering logic. Every workflow delegates to `runtime/verify.py` (or to a script in `.github/scripts/` that is invoked by `verify.py`).

## 3. Runtime Ownership

`runtime/verify.py` is the **single execution layer** for all verification workflows.

- It reads profiles from `runtime/foundation/verification/profiles.py`.
- It generates reports to `runtime/generated/verification-report.md`.
- It records events via the observability layer.
- It provides the `status` command for CI summaries.

**Rule:** No workflow may implement verification logic in YAML. All logic lives inside the runtime.

### Local/CI Parity

Every CI command must have an identical local equivalent:

| CI Command | Local Command |
|------------|---------------|
| `python runtime/verify.py backend` | `python runtime/verify.py backend` |

## 4. Composite Actions

All workflows use the five canonical composite actions. No workflow may inline the logic these actions encapsulate.

| Action | Responsibility | Used By |
|--------|---------------|---------|
| `setup-python-runtime` | Python 3.12, pip cache, root + backend deps, verification tooling | `bootstrap-runtime` |
| `setup-node-runtime` | Node.js 20, npm cache, frontend deps | frontend, playwright, release, dependency-update |
| `setup-playwright` | Playwright browser install with cache | playwright |
| `bootstrap-runtime` | Python setup, cross-layer map, knowledge index, version validation, workspace seeding | All verification workflows + dependency-update |
| `upload-runtime` | Standardized artifact upload with retention policy | All workflows |

**Rules:**
- All repeated setup logic lives inside these actions.
- No workflow may duplicate `actions/setup-python`, `actions/setup-node`, `actions/cache`, or `actions/upload-artifact`.
- New composite actions must be added to this table.
- Every composite action must have an `action.yml` at its root.

## 5. Naming Conventions

### Workflow Names
- Kebab-case: `backend-verify`, `frontend-verify`, `verification-runtime`
- Short and descriptive
- Match the `name:` field in the YAML

### Job Names
- Lowercase with hyphens: `verify`, `test`, `quality`
- Contextual when needed: `verify-runtime`, `dependency-health`

### Step Names
- Capital case, verb-first: `Checkout code`, `Bootstrap Engineering Runtime`
- Action description: `Upload shared artifact — cross-layer-map`, `Job Summary`

### Artifact Names
- Dash-separated: `cross-layer-map`, `backend-report`, `mutation-evidence`
- Unique within a workflow run
- Do not include `run_id` or `sha` — the workflow run ID is unique enough

## 6. Trigger Philosophy

| Trigger Type | When to Use | Examples |
|-------------|-------------|----------|
| `push` | Automatic on every branch push (with path filters) | backend-verify, frontend-verify, quality |
| `pull_request` | Block merges; limited to main/develop | backend-verify, frontend-verify |
| `schedule` | Recurring nightly/weekly jobs | golden (daily), mutation (daily), dependency-update (weekly) |
| `workflow_dispatch` | Manual invocation with optional inputs | All workflows |
| `release` | Triggered on published GitHub releases | release |

**Rules:**
- Verification workflows must use path filters on push triggers to avoid unnecessary runs.
- `quality.yml` intentionally has no path filter — it is a fast gate on every change.
- Scheduled workflows must use `cancel-in-progress: false` (see Rule 7).

## 7. Path Filtering

Every verification workflow with a `push` trigger must define `paths` filters.

| Workflow | Push Paths | PR Paths |
|----------|-----------|----------|
| `backend-verify.yml` | `backend/**`, `runtime/**` | `backend/**`, `runtime/**` |
| `frontend-verify.yml` | `frontend/**`, `backend/src/routers/**`, `backend/src/mappers/**`, `runtime/**` | same |
| `verification-runtime.yml` | `runtime/**`, `backend/src/engines/**`, `backend/src/routers/**`, `backend/src/mappers/**` | same |
| `playwright.yml` | `frontend/**`, `e2e/**`, `runtime/**` | same |
| `quality.yml` | *(none — fast gate on all)* | *(none — fast gate on all)* |

**Rule:** Path filters must cover all directories that affect the verification scope. Missing path filters on verification workflows are a violation.

## 8. Retention Policy

| Artifact Category | Retention |
|-------------------|-----------|
| verification | 14 days |

| mutation | 90 days |
| golden | 90 days |
| release | 90 days |

**Rule:** Use the `upload-runtime` composite action for all artifact uploads. Never inline `actions/upload-artifact`.

## 9. Concurrency

Every workflow must define a `concurrency` block:

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

**Exceptions (never cancel):**

| Workflow | Reason |
|----------|--------|
| `golden.yml` | Nightly regression — must complete for historical comparison |
| `mutation.yml` | Slow mutation testing — cancellation wastes GPU/CPU time |
| `release.yml` | Release artifacts must be produced |

---

## 10. Job Summaries

Every verification workflow must append its summary to `GITHUB_STEP_SUMMARY` at the end:

```yaml
- name: Job Summary
  if: always()
  run: |
    echo "## ${{ github.workflow }} — Run #${{ github.run_number }}" >> $GITHUB_STEP_SUMMARY
    echo "" >> $GITHUB_STEP_SUMMARY
    python runtime/verify.py status >> $GITHUB_STEP_SUMMARY
```

**Rule:** This is the standard CI report. No workflow may use a custom summary format.

## 11. Rules for Future Workflow Additions

When adding a new workflow, you MUST:

1. [ ] Define a single responsibility that maps to one `verify.py` profile command.
2. [ ] Use the `bootstrap-runtime` composite action (never inline setup).
3. [ ] Use the `upload-runtime` composite action for all artifact uploads.
4. [ ] Define a `concurrency` block with the standard group pattern.
5. [ ] Add path filters to `push` triggers (unless the workflow is a fast gate).
6. [ ] Append a `Job Summary` step using `python runtime/verify.py status`.
7. [ ] Ensure the profile command matches the workflow's responsibility.
8. [ ] Do not duplicate artifact names from existing workflows.
9. [ ] Update `docs/GITHUB_ACTIONS_V2_AUDIT.md` with the new workflow.
10. [ ] Run `.github/scripts/validate_actions.py` — must pass with zero errors.
