## 1. EXECUTIVE DETERMINATION

**The repository does NOT yet have one coherent, deterministic configuration and execution model.** It has a *strongly converging* model with several **intentional multi-project boundaries** that are legitimate, plus a small set of **accidental inconsistencies** and **latent parity risks** that can produce non-deterministic outcomes under specific (but common) local conditions.

The architecture is best classified as **Architecture C variant (monorepo with explicit subsystems)**: a root verification package (`clarinfin-verification`) + a backend source-only tree + a separate frontend (Node) project + a common Python toolchain in a single root `.venv`. This is *fundamentally sound* and matches the architectural constraints from M9-C42.9. The defects are in *configuration authority clarity* and *command-resolution determinism*, not in the boundary topology itself.

**Three things must be fixed before declaring "one coherent model":**
1. **Ruff has two physical configs with conflicting `line-length` (100 vs 88)** and only one carries a rule set — this is a genuine, accidental conflict, not a legitimate scope boundary.
2. **Bare `python3` fallbacks exist in scripts** (`scripts/verify-fast.sh`, `.github/scripts/run_*.sh`) that can resolve to a developer's *user-site* Python packages instead of the pinned `.venv`, breaking local/CI parity.
3. **Mutation config is dynamically rewritten in-tree** (`backend/pyproject.toml` `[tool.mutmut]` mutated at runtime, restored in a `finally` block). This is safe-but-fragile: a `SIGKILL`/OOM-kill leaves `backend/pyproject.toml` in a per-engine state and is not self-healing.

Everything else (single dependency authority, root package, `.venv` canonical environment, `verify.py` single entry point, CI delegation through `bootstrap-runtime`, frontend as a separate Node project) is **intentional and correct**.

## 4. PYTHON PROJECT-BOUNDARY FORENSICS

### Three candidate architectures

**Architecture A (current): root package + backend source-only + pytest-managed import path**
- `clarinfin-verification` (root) installs `runtime/*` via `[tool.setuptools.packages.find] where=["."] include=["runtime*"]`.
- `backend/src` is NOT a package; it is placed on `sys.path` by `backend/pyproject.toml` `pythonpath = ["src","tests"]` so `from src.engines...` works under pytest.
- Backend deps declared in root `pyproject.toml` (M10 single authority).
- **Evidence:** `backend/src/api.py:1` `from src.config import settings`; `backend/tests/conftest.py` patches mutmut; `backend/pyproject.toml` has NO `[project]` section.

**Architecture B: backend becomes an independently installable package**
- `backend/` would gain its own `[project]` + `pyproject.toml` packaging, `backend/src` → `backend/src/clarifin_backend` or installed as `src` package.
- Would remove the pytest `pythonpath` hack and the `src.` trampoline problem *if* the package were renamed away from `src`.

**Architecture C (current classification): monorepo with explicit packages**
- Root package + backend source tree + frontend Node project + shared toolchain.

### Evaluation against evidence

| Criterion | A (current) | B (package backend) | C (as-is monorepo) |
|-----------|-------------|---------------------|---------------------|
| Imports | `from src...` requires pytest pythonpath | would need `from clarifin_backend...` refactor (~hundreds of files) | same as A |
| Packaging | root pkg only; backend not installed | backend installed editable | root pkg only |
| Editable install | `pip install -e ".[all]"` installs runtime | + backend editable | same as A |
| pytest | works via pythonpath | works natively | works via pythonpath |
| **Mutation testing** | **trampoline rejects `src.` → needs conftest patch** | **eliminates trampoline issue if renamed** | same as A |
| mypy | `mypy backend/src` with pythonpath/extraPaths | native package | same as A |
| coverage | `.coveragerc source=src` | package-based | same |
| IDE/tool | works (pyright extraPaths) | cleaner | works |
| CI | works (verify.py) | works | works |
| Dependency mgmt | single root authority (good) | dual authorities (regression to M10 problem) | single root authority |
| Local/CI parity | good (one venv) | good (two installs) | good |
| Maintainability | `src.` coupling is unusual but contained | large refactor, high risk | contained |
| Runtime verification | native (root pkg) | native | native |
| Path determinism | `pythonpath` set by pytest ini (deterministic) | better | deterministic |
| Accidental PYTHONPATH | only via pytest ini + few tools/sys.path hacks | fewer | same |

**Determination:** Architecture A/C (current) is the **correct long-term choice** for THIS repository because:
1. It preserves the M10 single-dependency-authority decision (no dual `pyproject.toml` dependency declarations).
2. The `src.` import prefix is the *only*thing causing the trampoline issue, and that is solvable **without renaming the package** (see §10).
3. Converting backend to a package (B) would reintroduce the exact dual-authority problem M10 eliminated, and require a massive import rewrite across hundreds of files for marginal benefit.

**Conclusion:** Keep Architecture A/C. The "Architecture C classification" from M9-C42.9 is **CONFIRMED as the best long-term architecture**. The real defect is not the boundary but the *configuration authority clarity* within it (Ruff conflict, mutation in-tree rewrite, bare-python fallbacks).

### Enterprise abstraction determination

The correct abstraction is **NOT** "replace everything with `.venv/bin/...`". The correct abstraction is:

1. **One canonical launcher**: `scripts/verify.sh` (already exists, already sets `PATH=.venv/bin:$PATH`). All local entry points should go through it.
2. **One environment resolver**: `runtime/foundation/verification/env.py` (already exists; `_resolve` prefers `.venv/bin` then PATH). This is the right pattern and should be the ONLY place that resolves tool binaries.
3. **One verification CLI**: `runtime/verify.py` (exists; all workflows use it).
4. **One tool-execution layer**: mutation_runner already calls `env.py` to get the mutmut binary and prepends `VENV_BIN` to PATH — **this is the correct pattern** and should be replicated for pytest/ruff/mypy invocations instead of bare `python3 -m`.
5. **PATH-independent subprocess execution**: subprocess calls must always pass `env={"PATH": f"{VENV_BIN}:{os.environ['PATH']}"}` (as mutation_runner does) rather than relying on inherited PATH.
6. **Explicit interpreter discovery**: `env.py` already does this. Extend it: add `resolve_tool("pytest")`, `resolve_tool("ruff")`, `resolve_tool("mypy")` helpers returning absolute `.venv/bin` paths, and have `profiles.py` use them instead of bare `python3 -m`.

**Special question — `python` vs `python3` vs `.venv/bin/python`:**
- `python` is **NOT a project convention** (pre-commit `.pre-commit-config.yaml` explicitly fails on bare `python`; repository convention is `python3`).
- `python3` is the convention. It must always resolve to the **controlled interpreter** (`.venv/bin/python3` locally, runner python in CI).
- `.venv/bin/python` and `.venv/bin/python3` are the same binary (symlink). Using `.venv/bin/python` explicitly is the safest local form.
- **Policy:** Treat `python` as prohibited (pre-commit already enforces). Treat `python3` as "controlled interpreter" — never let it fall back to a system/user-site python. The ONLY safe forms are (a) `.venv/bin/python` (local), (b) `python` as resolved by `actions/setup-python` in CI (which installs deps into that python), or (c) any invocation that goes through `verify.sh` / `env.py` which guarantee `.venv/bin` precedence.

### Material differences identified

1. **CI does NOT enforce `requirements.lock`.** Local `pip install -e ".[all]"` resolves from `pyproject.toml` (exact pins there). `requirements.lock` is a *regenerable snapshot* but CI never consumes or validates it. 2. **Local Playwright/Node may be absent.** `scripts/bootstrap.sh` runs `npm ci` in frontend, but `scripts/verify.sh` does NOT invoke node setup. A developer running `verify.sh playwright` without a bootstrapped frontend gets a failure. CI always sets up node. **(MED)**

5. **OS/locale/tz not pinned.** Not validated. **(LOW, UNVERIFIED)**

### Formal definition of "local/CI parity" for this repo

> Every verification command, when executed locally via `./scripts/verify.sh <profile>` and in CI via `python runtime/verify.py <profile>` (after `bootstrap-runtime`), MUST:
> (a) resolve the same tool binary versions (from the single root `pyproject.toml` pin set),
> (b) execute with the same working directory and configuration discovery,
> (c) produce bit-comparable evidence artifacts,
> (d) require no manual environment setup beyond `scripts/bootstrap.sh`.

Currently (a)(b)(c) hold **when invoked through `verify.sh`**; they are **violated** when `.github/scripts/*.sh` are reached with a non-venv-PATH shell (which is the normal local path through `profiles.py`).

## 9. MUTATION INFRASTRUCTURE ARCHITECTURE

### Components reviewed
- `runtime/foundation/verification/mutation_runner.py` (execute_mutation, write_backend_mutmut_config, _restore_source_tree, _validate_cache)
- `runtime/foundation/verification/mutation_contract.py` (ENGINE_SELECTION, render_mutmut_config_block, write_backend_mutmut_config)
- `backend/pyproject.toml [tool.mutmut]` (static full-scope fallback)
- `backend/tests/conftest.py` (trampoline patch)
- `backend/tests/mutation_infra/` (smoke fixture: probe.py, test_probe.py, pyproject.toml)
- `backend/mutants/` (git-ignored working copy)

### Analysis of the 10 required questions

**1. Why is configuration dynamically rewritten?**
`mutation_runner.execute_mutation` (mode `target`/`full`) calls `write_backend_mutmut_config()` which **rewrites the `[tool.mutmut]` section of `backend/pyproject.toml`** from `ENGINE_SELECTION` (mutation_contract.py:272). The original block is saved (`installed_config_original`) and restored in a `finally` block (mutation_runner.py:369-370). **Reason:** mutmut 3.7.0 reads its config from the nearest `pyproject.toml`/`setup.cfg`/`tox.ini` at the mutation `cwd` (backend/). The engine-specific `source_paths` + `pytest_add_cli_args_test_selection` must be per-engine, so the runner renders them per run. **(VERIFIED — intentional, C42.7)**

**2. Does mutmut support a safer config mechanism?**
mutmut 3.7.0's `Config` loads from `[tool.mutmut]` in pyproject/setup.cfg/tox.ini. It does **NOT** support a `--config-file` CLI override for the mutation config (only `paths_to_mutate` legacy). So the in-tree rewrite is currently the *only* way to scope per engine without a separate project dir. **(VERIFIED — no built-in alternative)**

**3. Is a temporary isolated mutation project possible?**
YES. Instead of mutating `backend/pyproject.toml` in-tree, the runner could:
- Copy `backend/` to a temp dir (or use `backend/mutants/` which already exists as a working copy), OR
- Write a *separate* `mutmut` config in a temp `pyproject.toml`/`setup.cfg` in a temp dir that `source_paths` points into backend (mutmut only mutates `source_paths`; tests run from backend).
- Run mutmut with `cwd` = that temp dir.
This would **eliminate the in-tree rewrite entirely**. **(LIKELY feasible — not validated)**

**4. Can subprocess isolation eliminate source config mutation?**
YES — Option 3 above. The mutation cache (`backend/.mutmut-cache`) and `backend/mutants/` are already outside the committed tree. Only `backend/pyproject.toml` is mutated in-tree. Isolating the config to a temp file/dir removes the only in-tree mutation. **(LIKELY)**

**5. Is signal handling sufficient?**
The restore is in a `finally` block (mutation_runner.py:365-370). `finally` runs on normal exit and Python exceptions, but **NOT on `SIGKILL` (OOM), `SIGSEGV`, or `os._exit`**. If the mutation subprocess is killed hard, `backend/pyproject.toml` is left in the per-engine state and `installed_config_original` is lost (it's an in-memory variable). **(VERIFIED fragile — HIGH)**

**6. Can process termination corrupt the repo?**
YES — a hard kill mid-run leaves `backend/pyproject.toml [tool.mutmut]` = single-engine scope. Next `git status` shows a modified tracked file. A developer who then commits would permanently change the canonical full-scope config. **(VERIFIED risk — HIGH)**

**7. Can parallel mutation runs interfere?**
`execute_mutation` removes `backend/mutants/` and `backend/.mutmut-cache` at start (mutation_runner.py:299-306). Two concurrent `verify.py mutation` runs would race on `backend/pyproject.toml` + `backend/.mutmut-cache` + `backend/mutants/`. CI runs mutation in a single job (mutation.yml: mutation needs mutation-smoke; no matrix), so CI is safe. **Local parallel runs are unsafe.** **(VERIFIED — MED, local-only)**

**8. Are smoke and full mutation semantics truly equivalent?**
**NO — by design.** Smoke (`backend/tests/mutation_infra/`) mutates a trivial `probe.py` with a hand-crafted `pyproject.toml` (source_paths=["probe.py"], runner="python3 -m pytest test_probe.py") and is **explicitly NOT a score** (mutation_contract: "NOT a mutation score"). Full mutates `src/engines/` against engine test suites with an 80% gate. They share the *infrastructure* (trampoline patch, mutmut binary, result parsing) but **different scope, config, and semantics**. The smoke proves "killed/survived/no-tests distinguishable"; full is the authoritative score. **(VERIFIED — intentional, not a defect)**

**9. Is the trampoline patch a legitimate adapter or an architectural smell?**
**Legitimate compatibility adapter, rooted in a deeper import-topology decision.**
- mutmut 3.7.0 `record_trampoline_hit` asserts `not name.startswith("src.")` (`.venv/.../mutmut/__main__.py:122`).
- ClariFin backend imports as `from src.engines...` (verified across `backend/src/**`). So mutated module names are `src.engines.credit_card_engine.utilization` → assertion fails.
- `backend/tests/conftest.py:33-61` patches `record_trampoline_hit` to strip the `src.` prefix **only when `MUTANT_UNDER_TEST` is set** (mutmut sets this env var during mutation runs). Normal pytest runs are unaffected.
- **Root cause:** the `src.` top-level package prefix. This is a *backend import-topology choice*, not a mutmut bug per se. The patch is the minimal, correct, project-owned workaround. It is **NOT** in site-packages (contradicts the M9-C42.9 fear of "modifying installed packages" — VERIFIED the patch lives in repo `backend/tests/conftest.py`, not in `.venv`).
- **Can it be permanently eliminated through architecture?** YES — if backend `src` were renamed to a non-`src.`-prefixed importable package (e.g. `clarifin_backend`), mutmut's assertion would pass natively. But that requires rewriting every `from src...` import (hundreds of files) and is a large, risky refactor with no functional benefit beyond removing the patch. **Recommendation: KEEP the trampoline patch; do NOT rename `src`.** The patch is small, scoped, and correct.

**10. Does backend import topology itself cause the trampoline requirement?**
**YES.** The `src.` prefix is the sole trigger. It is also why `backend/pyrightconfig.json` needs `extraPaths:["src"]` and `backend/pyproject.toml` needs `pythonpath:["src","tests"]` and `backend/.coveragerc` uses `source=src`. The `src` prefix is a **consistent, intentional backend convention** — it is not accidental, but it is the single point that forces three workarounds (trampoline patch, pytest pythonpath, pyright extraPaths). All three are legitimate and contained. **(VERIFIED)**

### Mutation architecture verdict
**Fundamentally sound**, with ONE fragility: **in-tree `backend/pyproject.toml` rewrite not safe against hard kill / parallel runs**. The fix is architectural (isolate mutation config to a temp project dir), NOT a behavior change. The trampoline patch is correct and should stay.

### Error handling
- `run_backend_verification.sh` collects per-phase exit codes (good, structured evidence).
- `run_fast_checks.sh` uses `set -e` and exits on first failure (less granular).

### CI/local branching
- `profiles.py` tasks invoke `.github/scripts/*.sh` which assume `python3` on PATH. Locally, `verify.sh` sets `PATH=.venv/bin` but `profiles.py` tasks run as subprocesses of `verify.py` — **does the subprocess inherit the modified PATH?** `verify.sh` does `export PATH=.venv/bin:$PATH` then `exec .venv/bin/python runtime/verify.py`. The `exec` replaces the shell, so `verify.py` and its child `bash .github/scripts/X.sh` inherit `PATH=.venv/bin:$PATH`. **So through `verify.sh`, the .github/scripts DO get .venv/bin first.** The parity gap (§7.3) only manifests if a developer runs `python runtime/verify.py backend` directly WITHOUT going through `verify.sh` (or runs the `.github/scripts` directly). **(REFINES §7.3: risk is real but narrower than "all local runs")**

### Canonical command layer recommendation
**Keep `scripts/verify.sh` as the ONLY local entry point** (it correctly sets PATH). Make `runtime/verify.py` and `profiles.py` the only internal orchestration; **deprecate `.github/scripts/run_*.sh`** (they are redundant with profiles.py tasks and bypass env.py resolution when called outside verify.sh). The CI workflows already call `verify.py` directly (not the scripts), so removing the scripts from profiles.py tasks and having profiles.py call `env.py`-resolved binaries directly would eliminate the duplication AND the parity gap.
