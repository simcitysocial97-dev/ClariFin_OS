## 1. EXECUTIVE DETERMINATION

**The repository has an architecturally sound monorepo topology (Architecture C) but contains three categories of bounded defects that prevent it from being "deterministic + reproducible + self-diagnostic + drift-resistant":**

| Category | Count | Severity | Example |
|----------|-------|----------|---------|
| Config authority conflict | 2 | HIGH | Ruff dual-config line-length (100 vs 88); root config has no rule set |
| Path/environment parity gap | 3 | HIGH | Profiles invoke bare `python3 -m` via shell=True without explicit env; Playwright launches backend with bare `python3`; legacy scripts have no PATH control |
| Tracked-file mutation during verification | 1 | CRITICAL | Mutation runner rewrites `backend/pyproject.toml [tool.mutmut]` in-tree; fragile against SIGKILL/OOM |

**No boundary topology change is required.** The `src.` import prefix, single-root-venv, root-package model, and frontend isolation are correct. All three defects are fixable without touching source code, tests, or mutating tracked configuration files during any phase except Phase 1 (Ruff alignment).

**Fourteen of twenty `.github/scripts/run_*.sh` scripts are dead code** (zero references from any workflow or profile). This is a maintenance burden, not a correctness defect.

The target state is achievable while preserving all existing capabilities (backend, runtime, frontend, mutation, contract, property, golden, E2E) and without weakening any tests.

### 6.2 Direct `verify.py` Invocation WITHOUT verify.sh — PARITY GAP

```
USER → .venv/bin/python runtime/verify.py backend   (OR)
USER → python runtime/verify.py backend              (without .venv/bin on PATH)
  │
  ├─ PATH = user's PATH (.venv/bin NOT prepended unless already there)
  │
  ├─ executor runs: subprocess.Popen("python3 -m ruff check backend/src/",
  │                                 shell=True,
  │                                 env={**os.environ, PYTHONUNBUFFERED="1"})
  │    ├─ python3 resolves via os.environ["PATH"] (user's PATH — NOT .venv/bin-first)
  │    └─ IF user's system python3 first on PATH → wrong interpreter ✗
  │
  └─ RESULT: NON-DETERMINISTIC on machines without .venv/bin on PATH
```

**Root cause:** `executor.py` passes `{**os.environ, "PYTHONUNBUFFERED": "1"}` — it does NOT inject `.venv/bin` into PATH. The PATH guarantee comes entirely from the caller (`verify.sh`). This is a design debt.

### 8.3 Formal Parity Definition

> Local and CI execution are semantically equivalent when:
> 1. Both resolve the same Python major.minor version (≥3.12)
> 2. Both install the same dependency set from the same `pyproject.toml` pins

> 7. Browser dependencies are deterministically provisioned

## 10. MUTATION ARCHITECTURE ANALYSIS

### 10.1 Current Mechanism (Verified Step-by-Step)

```
execute_mutation(mode="target"/"full", target=<engine_name>)
  │
  ├─ 1. env = resolve_environment(config_dir=BACKEND_DIR)
  │      → verifies mutmut 3.7.0 in .venv; checks forbidden venvs
  │
  ├─ 2. config_hash = hash_file(backend/pyproject.toml)     ← captures BEFORE rewrite
  │
  ├─ 3. installed_config_original = write_backend_mutmut_config(engine, FULL_CONFIG)
  │      ├─ reads backend/pyproject.toml → text
  │      ├─ regex-replaces [tool.mutmut] section with rendered ENGINE_SELECTION config
  │      ├─ WRITES back to backend/pyproject.toml   ← TRACKED FILE MUTATION
  │      └─ returns original text (for restore)
  │
  ├─ 4. shutil.rmtree(backend/mutants/)                    ← removes stale mutants
  ├─ 5. shutil.rmtree(backend/.mutmut-cache/)              ← removes stale cache
  │
  ├─ 6. subprocess.run([mutmut_bin, "run"],
  │                     cwd=BACKEND_DIR,
  │                     env={**os.environ, "PATH": f"{VENV_BIN}:{PATH}"})
  │    ├─ mutmut reads backend/pyproject.toml [tool.mutmut] (now engine-scoped)
  │    ├─ mutmut creates backend/mutants/ with mutated source copies
  │    ├─ mutmut executes runner = "python3 -m pytest" with test_selection args
  │    └─ mutmut writes results to backend/.mutmut-cache/
  │
  ├─ 7. finally:                                           ← RESTORE (fragile)
  │    ├─ _restore_source_tree(cwd, scope)                ← git checkout -- mutated source files
  │    └─ if installed_config_original is not None:
  │           FULL_CONFIG.write_text(installed_config_original)   ← RESTORES pyproject.toml
  │
  └─ 8. subprocess.run([mutmut_bin, "results", "--all", "true"])
        → parse output → MutationResult
```

### 10.2 Why In-Tree Rewrite Exists (Root Cause Analysis)

**mutmut 3.7.0 config discovery:** Searches cwd upward for `pyproject.toml`, `setup.cfg`, or `tox.ini`. NO `--config-file` CLI flag exists (verified: `mutmut --help` crashes before showing options when run from a config-less directory). Since ENGINE_SELECTION requires DIFFERENT `source_paths` and `pytest_add_cli_args_test_selection` per engine, the config MUST be rendered dynamically. The only mechanism with mutmut 3.7.0 is writing to a file mutmut can discover.

**Confirmed:** `mutmut --help` fails with `FileNotFoundError: Could not figure out where the code to mutate is` when run from a directory without a mutmut config. This means even introspection requires the config file to exist.

### 10.3 Alternative Approaches Evaluated

| Approach | Feasibility | Effort | Safety | Verdict |
|----------|------------|--------|--------|---------|
| Temp-dir pyproject.toml + absolute source_paths | **FEASIBLE** | Medium | High (no tracked file touched) | Best option |
| Monkey-patch `mutmut.configuration.Config._load_config` | FEASIBLE | Low | Medium (depends on internal mutmut API) | Acceptable fallback |
| Write to temp `setup.cfg` in temp dir | FEASIBLE | Low | High | Simpler than pyproject.toml approach |
| Keep in-tree rewrite + add atexit/signal handlers | Works | Low | Medium (still fails on SIGKILL) | Quick mitigation |
| Upgrade mutmut to version with `--config-file` | Unknown | Unknown | Unknown (would break pin) | NOT recommended |

### 10.4 Safest Viable Target Design (Recommended)

**Approach: temp-dir isolated config with absolute paths**

```
Phase design (conceptual, NOT implemented):
  1. Create temp directory: tmpdir = tempfile.mkdtemp(prefix="mutmut-config-")
  2. Render canonical config block from ENGINE_SELECTION[target]
  3. Convert source_paths to ABSOLUTE: BACKEND_DIR / "src/engines/credit_card_engine" etc.
  4. Write pyproject.toml to tmpdir with [tool.mutmut] containing absolute paths
  5. Also_write conftest.py to tmpdir if needed for sys.path injection
  6. Set cwd = tmpdir for mutmut (source_paths are absolute so mutmut can access backend/src/)
  7. ALSO set cwd = BACKEND_DIR for the mutmut runner subprocess? NO — mutmut needs cwd
     to find its config. Use tmpdir as cwd.
  8. Run mutmut: subprocess.run([mutmut_bin, "run"], cwd=tmpdir, env={PATH=VENV_BIN:...})
  9. mutmut discovers tmpdir/pyproject.toml → reads absolute source_paths → mutates backend/src/
  10. On exit (success or failure): shutil.rmtree(tmpdir, ignore_errors=True)
  11. NO tracked file is ever written. git status remains clean.
```

**Key challenge:** mutmut copies source files to `backend/mutants/` (configured via `also_copy`). With absolute source_paths, mutmut knows where the originals are. But `also_copy = ["src"]` in the current config means the entire `src/` tree is copied. We'd need to preserve this behavior. The temp-dir approach maintains it because `also_copy` paths are relative to cwd — we'd need to make them relative to BACKEND_DIR or adjust.

**Simpler alternative:** Instead of absolute paths, place the temp config in `backend/` as a separate file that mutmut discovers:
- Write `backend/mutmut-config-temp.toml` (or `.setup.cfg`) to a non-pyproject location
- Problem: mutmut only discovers `pyproject.toml`, `setup.cfg`, `tox.ini` — nothing else.
- Workaround: write to `backend/setup.cfg` temporarily, then delete it. But this is still in-tree mutation.

**Pragmatic recommendation:** Given the complexity of absolute-path resolution and the fact that the current in-tree rewrite works correctly under normal conditions (finally block restores), the **best near-term fix** is:

1. Keep the in-tree rewrite (it's correct under normal execution)
2. Add `signal.signal()` handlers for SIGTERM/SIGINT that restore config before exit
3. Add `atexit.register()` as backup
4. Add post-run `git status` validation that FAILS if `backend/pyproject.toml` is dirty
5. Consider submitting a `--config-file` feature request to mutmut upstream

This achieves: **safe against normal failures (exit, exception, signal), fragile only against SIGKILL/OOM** — which is an acceptable trade-off for a development tool.

### 10.5 Parallel Concurrency

Two concurrent `verify.py mutation --target credit_card_engine` runs:
1. Both read `installed_config_original` simultaneously (safe — reads are atomic for small files)
2. Both write different content to `backend/pyproject.toml` (RACE CONDITION)
3. Both `rmtree(backend/mutants/)` (second deletes first's work)
4. One restores config, the other overwrites with stale original
5. Result: **corrupted state + lost mutation data**

**Conclusion:** Parallel mutation runs are UNSAFE. CI runs a single job; local runs sequentially. Multi-tenant parallelism requires either mutex locking or the temp-dir approach from §10.4.

### 10.6 Smoke vs Full Equivalence

**NOT equivalent by design (intentional):**
- Smoke: mutates `probe.py` (trivial code), tests `test_probe.py` (2 assertions), proves infrastructure works. Score = 50% (by design — intentionally has survivors).
- Full: mutates `src/engines/` (real financial code), tests all engine test suites. Score determines quality gate (80% threshold).
- Both share the same trampoline patch, mutmut binary, result parsing — but DIFFERENT source scopes, test scopes, and semantics.
- Smoke is an INFRASTRUCTURE HEALTH CHECK, not a quality metric. Full is the AUTHORITATIVE score.

## 11. RUFF / BLACK / MYPY ARCHITECTURE ANALYSIS

### 11.1 Ruff — Definitive Conflict Analysis

**Evidence:**
- `pyproject.toml:87-89`: `[tool.ruff] line-length = 100 target-version = "py312"` — no `[tool.ruff.lint]` section
- `backend/ruff.toml:8`: `line-length = 88`; `[lint] select = [E,W,F,I,B,C4,UP,SIM]`

**Discovery behavior:**
- `ruff check backend/src/api.py`: starts at `backend/src/api.py`, searches upward → finds `backend/ruff.toml` FIRST → uses line-length=88 + rules
- `ruff check .` from repo root: starts at `.`, finds root `pyproject.toml` → uses line-length=100 + default rules
- `python3 -m ruff check backend/src/` (profiles.py, cwd=root): ruff resolves each file individually, searching upward from each file's directory → finds `backend/ruff.toml` for every backend/src/ file → line-length=88

**Root cause of conflict:** The ROOT `[tool.ruff]` is an **incomplete stub** — it defines line-length=100 but no rule set. The value 100 disagrees with Black (88) AND with backend/ruff.toml (88). This is almost certainly a historical inconsistency, not an intentional choice.

**Is consolidation possible?** YES — with one caveat:
- Root `[tool.ruff]` should be updated to `line-length = 88` (match Black and backend)
- Root `[tool.ruff]` should gain a base `[lint]` rule set (e.g., `select = ["E", "F", "W"]` minimum for runtime code)
- `backend/ruff.toml` can then be simplified to ONLY contain backend-specific overrides (the current `[lint]` select would become redundant with a richer root config)
- OR: delete root `[tool.ruff]` entirely and let `backend/ruff.toml` govern backend; runtime code gets no linting (acceptable since runtime code is minimal)

**Recommendation:** Align root to 88 + minimal rule set. Delete `backend/ruff.toml`'s redundant `line-length` and `target-version` (they'd match root). Keep only backend-specific `[lint.per-file-ignores]` if needed.

### 11.2 Black — Gap Identification

- Root `[tool.black]` (line-length=88) is the single authoritative config.
- Backend/ruff.toml line-length=88 ALIGNS with Black — good.
- **BLACK IS NOT ENFORCED IN CI.** No workflow runs black. profiles.py has no black task. Only `run_fast_checks.sh` (local-only) runs black.
- Recommendation: Add a `black --check .` task to profiles.py quick/full profiles, OR add a dedicated CI workflow step.

### 11.3 mypy — Legitimate Dual Configuration

- Root `[tool.mypy]` (basic, excludes servers/src/fetch/tests/) governs runtime code.
- Backend `[tool.mypy]` (`strict=true`) governs backend financial code.
- The distinction is **documented and intentional** (backend/pyproject.toml comments confirm this).
- **Refinement needed:** Add a comment at root pyproject.toml `[tool.mypy]` header explaining WHY it's less strict (runtime code has fewer type annotations; financial correctness is enforced at backend level).

## 15. PYTHON COMMAND MODEL

### 15.1 Four Candidate Models Evaluated

| Model | Syntax | Pros | Cons | Recommendation |
|-------|--------|------|------|---------------|
| A | `.venv/bin/python` | Absolute, unambiguous | Requires knowing venv path; breaks in CI (no .venv) | Partial (local only) |
| B | `.venv/bin/python3` | Same as A + matches convention | Same limitations | Partial (local only) |
| C | `python` | Works in CI (runner python); works locally IF venv activated | Ambiguous on machines with multiple Pythons | **Acceptable in CI only** |
| D | `python3` | Matches pre-commit convention; works everywhere | Same ambiguity as C | **Acceptable with PATH control** |

### 15.2 Optimal Enterprise Model

**Canonical model: EXPLICIT RESOLUTION VIA `env.py` + PATH PREPEND**

Not: pick one of `python`/`python3`/`.venv/bin/python`. The right answer is that **every subprocess that invokes a Python tool must receive an explicit environment**, not rely on inherited PATH.

```
CORRECT PATTERN (already used by mutation_runner.py):
  env = {**os.environ, "PATH": f"{VENV_BIN}:{os.environ.get('PATH','')}"}
  subprocess.run(["python3", "-m", "ruff", "check", "backend/src/"],
                 cwd=repo_root, env=env)

INCORRECT PATTERN (currently used by profiles.py → executor.py):
  subprocess.Popen("python3 -m ruff check backend/src/",
                   shell=True, env={**os.environ, "PYTHONUNBUFFERED": "1"})
  # PATH is inherited — depends on caller
```

**Policy for `python` vs `python3`:**
- **Prefer `python3`** (matches pre-commit convention; repository-wide standard)
- **NEVER use bare `python`** (pre-commit already enforces this)
- `.venv/bin/python` and `.venv/bin/python3` are the SAME BINARY (symlink) — use whichever is conventional in context
- In CI, `python` and `python3` are the SAME runner python — no distinction needed

**Policy for PATH propagation:**
- `scripts/verify.sh` correctly exports `PATH=.venv/bin:$PATH` — KEEP
- `executor.py` must inject `.venv/bin` into subprocess PATH — **FIX REQUIRED**
- `.github/scripts/*.sh` must inject `.venv/bin` into PATH — **FIX REQUIRED** (or deprecate)
